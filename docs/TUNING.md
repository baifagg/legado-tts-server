# 调参说明（每个默认值都是实测出来的）

> 本项目的默认参数不是拍脑袋定的。每个都对应一轮 A/B 实测。
> **改任何一个之前，先看这里的结论和代价**，然后按 [AGENTS.md §7](../AGENTS.md#7-改参数前必须做的回归cer-验证) 跑回归。

测试环境：RTX 3060 Laptop 12 GB / i5-12400F / 32 GB，OmniVoice 0.8B fp16。
文本：真实小说长句（42–53 字），每档 2 句 × 多轮取中位。

---

## 1. `MODEL_SPEED_MAX = 1.6` —— 最重要的一个数

### 结论

模型侧语速上限从 **2.0 降到 1.6**，差额交给 ffmpeg atempo。总倍速不变，但**不再丢句首字**。

### 怎么测出来的

用 Whisper 逐字回读，25 个音色 × 3 句，比较「模型侧 2.0」和「模型侧 1.6」：

| 音色 | 模型侧 2.0 的 CER | 模型侧 1.6 的 CER | 改善 |
|---|---|---|---|
| 白露 | 0.260 | **0.035** | −87% |
| 小满 | 0.198 | **0.035** | −82% |
| 苏禾 | 0.133 | **0.035** | −74% |
| 温言 | 0.250 | **0.045** | −82% |
| 许南 | 0.240 | **0.042** | −82% |
| 女中年 | 0.238 | **0.025** | −89% |
| 王宝 | 0.025 | 0.025 | 持平 |

**25 个音色里 22 个在 2.0 下会丢字**，降到 1.6 后 23/25 落到 CER ≤ 0.10。

### 代价

合成耗时 **+7%~22%**（模型说慢话要多生成 token）。
但这项代价被 §2 的 `num_step` 32→16（−45%）完全覆盖，**净效果仍然更快**。

### 为什么不是 atempo 的锅

交叉验证：把 2.57× 的输出用 atempo 拉回 1.0× 再 ASR，CER 依然高 → 说明是**生成阶段就少字**，不是拉伸造成的。

### 分档实测（同一句，只改模型侧上限）

| 目标总倍速 | 模型侧 cap 2.0 | cap 1.85 | cap 1.7 | **cap 1.6** | cap 1.5 |
|---|---|---|---|---|---|
| 2.57× | 0.265 | 0.250 | 0.150 | **0.045** | 0.045 |
| 2.57× | 0.240 | 0.185 | 0.148 | **0.035** | 0.037 |

cap 1.6 是「刚好够」的拐点：再往下不涨收益，只增加耗时。

## 2. `NUM_STEP = 16` —— 第二重要

### 结论

采样步数 32 → 16。官方文档原文："Use 16 for faster inference."

| num_step | 单句中位 | 相对 | 变速后 CER |
|---|---|---|---|
| 32（旧默认） | 1291 ms | 1.00× | 0.105 |
| **16（当前）** | **713 ms** | **1.81×** | 0.080 |
| 12 | 551 ms | 2.34× | 0.096 |

- 16 步质量不劣于 32 步（CER 0.080 vs 0.105，n=16 有噪声但方向不差）
- 12 步已到「更快但开始变糙」的区间，**不建议当默认**，可作为"极速档"给用户手动切

## 3. 试过但**没有收益**的优化（别再花时间）

这三条曾被列为"重点优化方向"，实测全部无效或更差：

| 方向 | 实测结果 | 结论 |
|---|---|---|
| **参考音色 prompt 预热复用** | 1315 ms vs 基线 1291 ms | 无收益。3 秒短参考的 `audio_tokenizer.encode()` 只有几十毫秒，被前向淹没了 |
| **关 CFG（guidance_scale=0）** | 1425 ms（更慢），CER 0.184（明显变差） | 负收益。源码里 cond/uncond 拼成同一个 `2B` batch，`gs=0` 只省 log_softmax 不省前向 |
| **关后处理（postprocess/pad/fade）** | 1319 ms vs 1291 ms | 无收益 |
| **微批 4 句** | 单句摊 1205 ms，只快 7% | 收益远小于预期；还要重构两把锁、首句延迟变长，不值得 |

**唯一有效的就是 `num_step` 和 `MODEL_SPEED_MAX`（后者是修 bug 不是提速）。**

## 4. 文本前端（`text_front.py`）

### 为什么必须有

旧链路 `clean_text → digits_guard` 的顺序是错的：`clean_text` 先把 `% / ² ℃ -` 删掉，
`digits_guard` 再想处理数字时语义已经没了。

| 原文 | 旧链路实际喂给模型的 | 模型读成 |
|---|---|---|
| 他吃了 **1/3** 个西瓜 | 他吃了 **13** 个西瓜 | 十三个 |
| 合同签于 **2024-11-10** | 合同签于 **202410** | 六位乱读 |
| 增长 **15%** | 增长 **15** | 十五 |
| 卖了 **3,500** 元 | 卖了 **三,五百** 元 | 三、五百 |

### 修法

```
新链：digits_guard_pro(text) → merge_fragments() → clean_text()
```

`digits_guard_pro()` 覆盖 17 类规则：日期 / 时间 / 百分比 / 千分位 / 分数 / 比例 /
序数 / 范围 / 电话 / 年代 / 代际 / 单位 / 大数万位 / 负温度 / 拉丁+数字，
并**保护 OmniVoice 拼音控制语法**（`HANG2` 的 2 不会被当数字）。

效果：89 句专项测试集，文本层正确率 **68/89 (76.4%) → 89/89 (100%)**，数字类 **3/20 → 20/20**。

### 另一个坑：标点被删

`_EMOJI_RE` 原来包含 `\u3000-\u303F`（CJK 标点区），把 `。、〈〉《》「」『』【】〔〕`
整片删掉。生产日志 63,727 条请求里 `。` 只出现 **295 次（0.46%）**。

已修：`_EMOJI_RE` 去掉该区间；`_KAOMOJI_RE` 白名单补回 `“”‘’「」『』【】〔〕`。
**删掉颜文字的能力保留**（`┗|｀O′|┛` 之类仍会被清）。

## 5. 语速映射（`speed_to_ratio`）

Legado 有两套语速刻度，服务端都要兼容：

| 刻度 | 参数 | 正常值 | 映射 |
|---|---|---|---|
| `scale=float` | 0.0–2.0 | 1.0 | 0.4× ~ 4.23×（非线性：1.7 是用户习惯点 2.56×） |
| `scale=speed` | 1–100 | 10 | 线性，10 → 1.0× |
| 不传 `scale` | — | — | 按数值自动判断（≤2.5 当 float） |

**注意 Legado 某些版本会把 `1.5` 传成 `15`**（×10），服务端已做兼容：

```python
if 100 >= val > 10 and scale == "float": val = val / 10
```

## 6. 输出处理（`_finalize_audio`）

模型原始输出峰值常顶到 0.9–1.0。手机端再开点音量就超过 0 dBFS 被硬削波 —— 听感就是"破音"。

处理三步：
1. 去直流偏置（否则削波不对称）
2. 峰值归一化到 **−2 dBFS（0.79）**
3. `tanh` 软限幅（k=0.85），只压瞬态尖峰

实测输出峰值稳定在 **0.621**，与参考音频（0.84 峰值再衰减）听感一致。

## 7. ffmpeg atempo 参数

- 单次只支持 0.5–2.0，超出由 `_time_stretch()` 串联多段
- 处理 3 秒音频约 **50 ms**，不是瓶颈
- 历史：曾手写 numpy 相位声码器，**能量掉 88%、噪声感高 22 倍**（就是用户听到的"破音"）。别再手写。

| 方案 | 时长 | 峰值 | RMS | 频谱平坦度 |
|---|---|---|---|---|
| 原始 | 3.34s | 0.790 | 0.1169 | 0.003529 |
| 手写相位声码器 | 1.69s | 0.720 | **0.0138** | **0.079886** |
| librosa | 1.67s | 0.372 | 0.0688 | 0.004051 |
| **ffmpeg atempo** | 1.68s | 0.680 | **0.1145** | **0.003110** |

## 8. 缓存

- key = `sha1(engine|ref|ratio|text)`，**不含 num_step / guidance**
- 意味着：调 `num_step` 不会让缓存失效（旧缓存仍返回旧质量！调完记得清缓存再测）
- 改文本前端会让**全部缓存失效**（key 里的 text 变了），首次听会慢几分钟

清缓存：
```bash
rm -rf cache/*        # Linux/macOS
Remove-Item cache\* -Recurse -Force   # Windows
```
